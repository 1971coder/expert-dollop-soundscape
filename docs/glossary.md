# Glossary

The vocabulary used inside AuralFlow. Two registers live here:

1. **Domain terms** (audio, modes, signals) — what the product talks about.
2. **Multi-agent scaffold terms** — the operating model inherited from the scaffold (parallelism rule, sentinel fence, etc.).

Skim this once before the first session. The terms are small in number but precise.

---

## Domain terms

## Adaptive controller

The component (in `Adaptive/`) that runs **off** the audio thread, reads signals (time-of-day, motion, heart rate, recent feedback), and writes parameter deltas onto the lock-free pipe consumed by `AudioEngine`. Deterministic, unit-testable. Lives in [architecture.md §2.2](architecture.md#22-adaptive--the-rules-engine).

## Audio render thread

The high-priority, system-owned thread that pulls audio buffers from the engine graph. **Sacred:** no allocations, no locking, no logging, no Swift `print`. Crossing this rule produces audible glitches that are very hard to debug. See [CLAUDE.md → Gotchas](../CLAUDE.md#gotchas).

## Binaural beats

A two-channel auditory technique where slightly different frequencies are sent to each ear, producing a perceived "beating" at the difference frequency. AuralFlow includes a `BinauralGenerator` node, **off by default**, and only enabled when headphones are detected and the user opts in. Implementation in `Audio/Nodes/BinauralGenerator.swift`.

## Brown noise

Noise whose power spectrum falls at 6 dB/octave (deeper / "rumbly" relative to pink or white). Generated by integrating white noise, which **drifts to DC over time** without a leaky integrator — apply a one-pole HPF at ~5 Hz. See `Audio/Nodes/NoiseGenerator.swift` and [requirements.md §2.4](requirements.md#24-local-first).

## Drone

A long, sustained, pitched audio layer with minimal harmonic motion. The base building block of Sleep mode and a major component of Focus and Relax. Implemented by `DroneSynth`.

## Focus mode

One of the four core user modes. Soft pulses, moderate brightness, light rhythmic motion (sub-audible). See [requirements.md §3.1](requirements.md#31-focus-mode).

## Leaky integrator

A one-pole high-pass filter (cutoff ~5 Hz in our usage) applied to brown-noise generation to prevent DC drift. Without it, brown noise will slowly slide toward DC and silently clip the woofer. The single most important detail in `NoiseGenerator`.

## Mode

A named, user-selectable configuration: Focus, Sleep, Relax, Walk. Each has a baseline `ModePreset` and a set of allowed adaptive rules. Modes never own session state — `SessionStateManager` does.

## Parameter delta

The data type passed from `AdaptiveController` to `AudioEngine` to change a parameter at runtime. Contains a `ParameterId`, a normalised value, and a ramp time. Pushed to a **lock-free SPSC ring buffer**; drained on the audio thread. See [api-contract.md §1](api-contract.md#1-audioengine-command-surface).

## Pink noise

Noise whose power spectrum falls at 3 dB/octave (gentler than white, brighter than brown). Common in Sleep and Relax modes.

## Procedural audio

Audio generated algorithmically in real time, rather than played back from recorded files. Every sound source in AuralFlow is procedural. **"Procedural" ≠ "random":** pure randomness is fatiguing; AuralFlow uses bounded stochastic + slow LFO modulation.

## Pulse modulator

A sub-audible LFO (typically 0.05–0.5 Hz) that modulates mixer channel gains to produce Focus mode's "soft pulse" character. Implementation in `Audio/Nodes/PulseModulator.swift`.

## Relax mode

Calm-but-awake relaxation. Tonal palette between Focus and Sleep. Phase 3 deliverable.

## Session

One bounded user listening session: a start, an active duration with a mode + preset, and (usually) an end. Persisted in SwiftData. Lifecycle owned by `SessionStateManager`. See [data-model.md](data-model.md#session).

## Sleep mode

One of the four core user modes. Dark tonal palette; heavy low-mid; slow drones; brown/pink noise; reduced treble. **Requires background audio entitlement** to keep playing with the screen locked. See [requirements.md §3.2](requirements.md#32-sleep-mode).

## SPSC ring buffer

Single-producer, single-consumer lock-free ring buffer. The one-way data pipe from the off-thread `AdaptiveController` (producer) to the audio render thread (consumer). The primitive that lets parameter changes happen mid-render without taking a lock.

## Walk mode

Outdoor walking ambience that responds to cadence (CoreMotion). Never matches step rate exactly. Phase 3 deliverable.

## Multi-agent scaffold terms

## Adoption recipe

The one-line `mkdir -p ...` block under each project-type recipe in [project-structure.md](project-structure.md). Designed to be copy-pasted into your terminal at adoption time so the documented directory shape exists after a single command. Claude Code itself can't run these because of the dangerous-commands hook (`rm -rf` is blocked) — that's intentional; copy-paste them yourself.

## Claim-checking

The conceptual model behind the multi-agent layer: each work package "claims" a bounded set of files via its *Files likely touched*, *Files explicitly excluded*, and **Shared Files Allowed To Change** sections. Two WPs whose claims overlap on shared files cannot run in parallel without explicit approval. The shared-file allow-list is the load-bearing primitive — it's how merge safety is enforced without a central coordinator.

## Cleanup signal

The audit failure that fires in `--strict` mode when a doc contains both the [scaffold-allow-empty](#scaffold-allow-empty-sentinel) sentinel **and** substantive content after it. Says: "you've started filling this doc in; remove the sentinel." Implemented by `has_content_after_sentinel` in [scripts/template-audit.sh](../scripts/template-audit.sh) (~lines 99–119).

## Decisions log

[decisions.md](decisions.md). Append-only record of significant architectural / engineering choices and their rationale. Distinct from [handoff.md](#handoff) (rolling state) and [architecture.md](architecture.md) (long-form structure). User-curated only — review commands must not write to it; they recommend entries instead.

## Delivery plan

[delivery-plan.md](delivery-plan.md). Single markdown table tracking every WP's status, agent, branch, dependencies, and shared-file risk. Pinned at the top: the [parallelism rule](#parallelism-rule). One row per WP file in [work-packages/](../work-packages/). Coordination primitive — keep WP file status and delivery-plan row in sync.

## Files explicitly excluded

A WP-template section listing files this WP must **not** touch, even if they would seem relevant. Often shared contracts, files owned by another in-flight WP, or files the WP author judges off-limits. Distinct from *Files likely touched* (allowed) and [Shared Files Allowed To Change](#shared-files-allowed-to-change) (allow-list of shared files).

## Files likely touched

A WP-template section listing the files this WP expects to create or modify. Best-guess; doesn't have to be exhaustive. Used for parallel-WP collision checks. A *positive* list — anything outside it is implicitly off-limits unless also listed in [Shared Files Allowed To Change](#shared-files-allowed-to-change).

## Foundation gate

[WP00-foundation.md](../work-packages/WP00-foundation.md). The mandatory first work package. Produces the project's twelve convention categories (project structure, error handling, testing, naming, etc.) which land in [coding-standards.md](coding-standards.md). **No feature work begins until WP00 closes.** The single most important rule in the scaffold's operating model.

## Handoff

[handoff.md](handoff.md). Rolling snapshot of the project's current state, open issues, assumptions, blockers, and next recommended steps. Maintained by [`/update-handoff`](../.claude/commands/update-handoff.md) at session end. **Not** an append-only log — overwriting and pruning are the point. Distinct from the [decisions log](#decisions-log), which *is* append-only.

## Integration drift

The slow accumulation of small inconsistencies between merged WPs: duplicated logic, divergent shared-types, stale `// TODO` markers, integration notes that were closed in code but not in the WP file. Detected by [`/integrate-feature`](../.claude/commands/integrate-feature.md). Findings travel via the report and via [handoff.md](#handoff); the integration command never refactors directly.

## Memory-write boundary

The explicit policy in each review command (`/integrate-feature`, `/qa-review`, `/architecture-review`) about which files it may update. Always: only [handoff.md](#handoff). Never: source code, tests, configuration, the WP file under review, [decisions.md](#decisions-log), or any other doc. Replaces the earlier ambiguous "read-only" framing.

## Parallelism rule

The bold rule pinned at the top of [delivery-plan.md](delivery-plan.md): *two work packages SHOULD NOT run in parallel if they both modify the same shared file or shared contract surface unless explicitly approved.* The primary mechanism for minimising merge conflicts and architectural drift. Compared via WPs' [Shared Files Allowed To Change](#shared-files-allowed-to-change) sets.

## Rolling snapshot

The shape of [handoff.md](handoff.md): each section is overwritten as state changes, not appended to. Closed issues drop out, stale assumptions get pruned, the *Current Snapshot* section is replaced verbatim. Contrast with [decisions.md](#decisions-log) (append-only). The distinction matters because append-only files rot into noise; rolling snapshots stay scannable.

## Scaffold-allow-empty sentinel

The HTML comment `scaffold-allow-empty` (full form: opening `<!--` plus the token plus closing `-->`) placed at the end of a doc that's intentionally a stub in a fresh scaffold. Acts as a **fence**: scaffold guidance / examples sit *above* the sentinel and are always allowed; project-specific content *below* the sentinel triggers the [cleanup signal](#cleanup-signal) in `--strict` audit. Used in [handoff.md](handoff.md), [delivery-plan.md](delivery-plan.md), [decisions.md](decisions.md), and the four short doc stubs (api-contract, data-model, testing-strategy, coding-standards). *(Glossary deliberately avoids writing the literal comment form so the audit doesn't treat this entry as a sentinel reset.)*

## Sentinel fence

See [scaffold-allow-empty sentinel](#scaffold-allow-empty-sentinel). The *fence* is the conceptual model — content above the sentinel is scaffold; content below is project. The audit's `has_content_after_sentinel` check enforces this asymmetry.

## Shared Files Allowed To Change

The most important section of [TEMPLATE.md](../work-packages/TEMPLATE.md). An explicit allow-list naming every shared / global file this WP is permitted to modify. Distinct from *Files likely touched* (best-guess) and *Files explicitly excluded* (negative list). Two WPs whose *Shared Files Allowed To Change* sets overlap **cannot** run in parallel — see the [parallelism rule](#parallelism-rule).

## Work package (WP)

A bounded unit of work, one markdown file in [work-packages/](../work-packages/). Named `WPNN-<slug>.md`. Lifecycle: `proposed` → `ready` → `in-progress` → `in-review` → `merged`. Authored via [`/create-work-package`](../.claude/commands/create-work-package.md), implemented via [`/start-agent`](../.claude/commands/start-agent.md). Each WP corresponds to one row in the [delivery plan](#delivery-plan) and one branch named `wp/NN-<slug>`.
